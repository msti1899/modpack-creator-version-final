## Specs

- S1: Each registered user belongs to at most one group, including group owners. Uniqueness is enforced by the database under concurrent requests.
- S2: A group has a name, a visibility (`public` or `private`), exactly one owner, and one membership row per member. Creating a group makes the creator its owner and first member. The creator must already have a profile.
- S3: Public groups allow any registered user with a profile and without a current group to join directly. Joining is idempotent for an existing member of that same group.
- S4: Private groups use an invitation link. Possession of the link does not grant membership: the invited user creates a pending join request and the owner must approve it. The owner may reject a pending request.
- S5: Only the owner may create/rotate the invitation, revoke it, approve or reject join requests, transfer ownership, or delete the group by leaving alone. Members may read their group and leave.
- S6: Ownership transfer is immediate when the owner names an existing member; it requires no acceptance. An owner with other members cannot leave without transferring. An owner who is the only member and leaves deletes the group (and future group-owned data) instead of leaving an ownerless group.
- S7: Cross-group isolation: a member reads only their own group's members; invitations and pending-request lists are owner-only. An invitation holder can inspect the target group ID/name, owner username and their own pending/member flags, not member lists or other users' requests. These response shapes implement the approved isolation requirement; they are not additional product visibility rules.
- S8: Rejected or failed writes leave no partial state. Admission races are arbitrated by database constraints, not by a separate availability lookup.
- S9: The API exposes the group contract over Hono, requires a verified Clerk session with `role: "authenticated"`, forwards the unchanged user token to Supabase Data API RPCs, validates inputs, and never uses service-role credentials.
- S10: Migration, database tests, API tests, guide, reference and delivery record ship with the behavior. Existing public Modrinth and profile behavior must not regress.
- S11: Group-name validation is identical at the SQL RPC, stored constraint and HTTP boundaries: surrounding Unicode whitespace is trimmed, the result is 1–60 characters, control characters and U+FEFF are rejected, and the stored form is readable through the HTTP contract.
- S12: Member and pending-request collections are paginated. The group overview embeds at most 50 of each with an opaque next cursor, and authenticated pages of at most 100 items keep every valid response within the API transport bound without an unapproved group-size limit.

Assumptions recorded during implementation (not new product requirements):

- Group names are trimmed and limited to 1–60 Unicode characters without control characters; names are not unique. This validation is an implementation limit, not the separate ASCII-only username rule.
- A private group has at most one active invitation token; the owner may rotate or revoke it. Tokens are 64 lowercase hex characters and do not expire in this delivery.
- Members may leave freely; the owner cannot remove members in this delivery because expulsion was not requested.
- No pack table exists yet; group deletion cascades group-owned rows added later.
